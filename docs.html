Getting Started

Overview

Therdal is a permissionless and verifiable stakeholder signaling protocol for Ethereum—giving ETH holders a credible way to express nonbinding preferences without claiming formal governance authority.

Nonbinding by design: Therdal measures real ETH-weighted sentiment across regular wallets and staked validators without introducing coin-voting capture over Ethereum protocol upgrades.

Four Decoupled Protocol Stages

Therdal separates topic creation, voter signing, batch publication, and cryptographic proof settlement so no single actor is trusted and voters can participate offline for $0 gas:

  1. Create a Topic: Anyone publishes a question, defines custom voting choices, records the Ethereum block-header snapshot at creation, and seeds a refundable USDC vote pool.
  2. Cast a Vote: ETH holders select an option backed by both wallet ETH and validator stake—signing offline for $0 gas or voting directly.
  3. Aggregate & Publish: Permissionless aggregators host voting frontends, collect offline signatures, and post compressed vote batches into Ethereum EIP-4844 blobs.
  4. Prove & Settle: Permissionless provers generate cryptographic validity proofs verifying signatures, snapshot balances, and uniqueness—updating the L1 tally and routing sponsored USDC rewards.

System Architecture

Therdal decouples topic creation, voter signing, EIP-4844 batch publication, and STARK tally settlement across three modular layers—so no off-chain operator is trusted, ETH is never locked, and ETH holders can signal offline for $0 gas.

Three-Layer Modular Design

  • Client, CLI & SDK Layer (frontend/, @therdal/sdk, therdal-cli, therdal-topics): Validates topics deterministically (THERDAL_TOPIC_V1), signs offline EIP-712 Vote envelopes, and builds historical EIP-1186 MPT & Beacon SSZ proofs for direct on-chain voting.
  • Permissionless Off-Chain Operator Layer (therdal-publisher, therdal-archive, therdal-prover, therdal-circuits): Independent Vote Aggregators pack signed ballots into canonical 31-byte EIP-4844 blobs and mirror raw blobs publicly; independent Batch Provers verify signatures, snapshot balances, KZG commitments, and 256-bit Sparse Merkle Tree (positionRoot) uniqueness out-of-order.
  • Ethereum L1 Settlement & Escrow Layer (Therdal.sol, SnapshotAuthenticator.sol, PositionEligibility.sol, StarkVerifierAdapter.sol, SponsorEscrow.sol, TherdalController.sol): Pins parent execution & beacon snapshot roots at creation, authenticates historical state roots, verifies STARK proofs over canonical 608-byte public inputs, splits settled vote fees (65% Batch Prover / 35% Vote Aggregator), and unlocks pro-rata unused refunds.

Core Concepts

Topics & Custom Options

Topics on Therdal are not restricted to binary Yes/No ballots. Creators register the subject, custom free-text voting options, and voting end timestamp directly on-chain.

Creating a Topic (Therdal.sol)

When calling createTopic(subject, options, votingEndsAt, initialSponsorship) (or createTopicWithConfig(CreateTopicParams)) on Therdal.sol, the protocol registers and validates:

  • Subject (string subject): Required, non-whitespace-only free-text prompt up to 512 UTF-8 bytes.
  • Custom Options (string[] options): Between 2 and 16 unique, non-whitespace-only free-text option strings (up to 256 UTF-8 bytes each, deduplicated after ASCII whitespace trimming)—for example, ["12 Blobs", "9 Blobs", "Keep at 6 Blobs"] or ["60M Gas", "45M Gas", "36M Gas", "No Change"].
  • Voting Ends (uint64 votingEndsAt): Future Unix timestamp (votingEndsAt > block.timestamp) defining when voting closes.
  • Automatic Parent Block Snapshot: Automatically pins snapshotBlock = block.number - 1 and snapshotBlockHash = blockhash(block.number - 1) at creation, plus deterministic contentHash (THERDAL_TOPIC_V1).
  • Free Creation & Optional Sponsorship: Creating a topic requires $0 deposit and $0 protocol fee. Any optional initialSponsorship (or top-up via sponsorTopic(topicId, amount)) deposits 100% into SponsorEscrow.

Topic Lifecycle Phases

Phase Condition Permitted Actions
Open now <= votingEndsAt Topic is active for signaling; anyone can call sponsorTopic(topicId, amount) to add USDC to the pool.
Closed / Settling now > votingEndsAt Voting window has ended; new sponsorships are closed and tally settlement proceeds in later protocol stages.
Finalized All published batches settled Final tallies locked; contributors call claimRefund for unused pool shares.
ClosedForRefunds now > settlementDeadline Settlement grace window closed; unused sponsored funds unlocked for pro-rata refunds.
Core Concepts

Snapshots & ETH Eligibility

Therdal measures voting weight from Ethereum block headers recorded at topic creation—counting both execution-layer wallet balances and consensus-layer staked validators without locking anyone's ETH.

Moving or buying ETH afterward has no effect: Because balances are proven against the block headers recorded when the topic was created, transferring, selling, or buying ETH after topic creation neither increases nor decreases a voter's weight, and voters never lock their funds.

Two-Step Snapshot Authentication

  1. Pin at Creation: createTopic automatically records snapshotBlock = block.number - 1, snapshotBlockHash = blockhash(block.number - 1), and EIP-4788 snapshotBeaconBlockRoot on-chain with minimal gas overhead.
  2. Authenticate Once per Topic: Either inline on the first direct vote or via authenticateExecutionSnapshot / authenticateBeaconSnapshot:
    • Execution Root: Verified against snapshotBlockHash (with BLOCKHASH / EIP-2935 0x0000F90827F1C53a10cb7A02335B175320002935 fallback), extracting stateRoot from the canonical RLP execution header.
    • Beacon Root: Verified against the pinned EIP-4788 snapshotBeaconBlockRoot (0x000F3df6D732807Ef1319fB7B8bB8522d0Beac02) with SHA-256 SSZ Merkle branches confirming alignment to snapshotBlockHash at leaf index 780.

Eligible ETH Positions

  • Execution Wallet Balances (THERDAL_WALLET): Proven via an EIP-1186 Merkle-Patricia Trie account proof against snapshotExecutionRoot where account == voter. Weight equals exact snapshot balance in wei.
  • Beacon Validator Stakes (THERDAL_VALIDATOR): Proven via an index-bound depth-40 SSZ Merkle inclusion branch against snapshotBeaconRoot. Requires slashed == false, activationEpoch <= snapshotEpoch < exitEpoch, and 0x01 or 0x02 withdrawal credentials matching voter.

Zero Double-Counting

Every counted wallet (THERDAL_WALLET) or validator (THERDAL_VALIDATOR) position key is permanently marked per topic so no wallet balance or validator index can be counted twice across direct votes or batch settlements.

Core Concepts · Stage 2

Direct Snapshot Voting

ETH holders can vote directly on-chain on any Open topic in Therdal.sol (IDirectVoting.sol) by submitting cryptographic proofs of Execution Layer ETH held at snapshot time, Beacon Chain ETH staked at snapshot time, or both—with $0 protocol fee and zero SponsorEscrow consumption.

Amortized Snapshot Authentication: Only the very first direct execution voter supplies rlpExecutionHeader and only the first validator voter supplies BeaconSnapshotAuthProof. Every subsequent voter passes empty auth bytes and verifies purely against the cached snapshotExecutionRoot and snapshotBeaconRoot.

1. Vote with Execution Layer ETH (voteWithExecutionBalance)

  1. Canonical RLP Header Check: SnapshotAuthenticator.sol and RLPReader.sol verify keccak256(rlpExecutionHeader) == snapshotBlockHash, check header field 8 == snapshotBlock, and cache snapshotExecutionRoot (field 3).
  2. EIP-1186 MPT Account Proof: MerklePatriciaProofVerifier.sol walks the Merkle-Patricia Trie proof along keccak256(abi.encodePacked(msg.sender)), RLP-decoding [nonce, balance, storageRoot, codeHash] directly from eth_getProof nodes.
  3. Nullifier Lock: Requires balance > 0, records walletKey = keccak256(abi.encodePacked("THERDAL_WALLET", block.chainid, msg.sender)), and adds balance wei to optionWeightsWei[optionIndex].

2. Vote with Beacon Chain Staked ETH (voteWithBeaconStake)

  1. EIP-4788 & Execution-Consensus Alignment: Authenticates BeaconBlockHeader.state_root (index 3) and slot (index 0, snapshotEpoch = slot / 32) against the pinned EIP-4788 snapshotBeaconBlockRoot, and verifies leaf index 780 proving latest_execution_payload_header.block_hash == snapshotBlockHash.
  2. Depth-40 SHA-256 SSZ Validator Proofs: SSZVerifier.sol hashes the 8-chunk Validator container via EVM SHA-256 precompile (0x02), traverses the 40-level validators tree strictly along the bit path of validatorIndex, mixes in validatorsLengthChunk (validatorIndex < validatorCount), and checks beaconStateBranch (depth 5 Deneb / 6 Electra) at field 11.
  3. Credential & Activity Rules: Enforces !slashed, activationEpoch <= snapshotEpoch < exitEpoch, and 0x01 (standard) or 0x02 (EIP-7251 MaxEB compounding) withdrawal credentials matching msg.sender, crediting effectiveBalanceGwei * 1 gwei wei under validatorKey.

3. Combined Atomic Voting (voteDirect)

// Prove both Execution ETH balance + multiple 0x01/0x02 staked validators in 1 transaction:
uint256 totalWeightWei = therdal.voteDirect(
    topicId,
    optionIndex,
    IDirectVoting.DirectVoteProofBundle({
        includeExecutionBalance: true,
        rlpExecutionHeader: rlpHeaderOrEmptyIfCached,
        rlpAccountProofNodes: eip1186ProofNodes,
        beaconAuth: beaconAuthOrEmptyIfCached,
        validatorProofs: validatorStakeProofs
    })

Core Concepts

Sponsored Funds & Fee Split

Offline voting is free for ETH holders because each topic holds an optional sponsored USD stablecoin pool—and all settled vote fees go directly to Vote Aggregators (35%) and Batch Provers (65%).

Free Topic Creation & Optional Sponsorships

  • Always Free Topic Creation ($0 Fee): Anyone can create a topic or referendum on Ethereum with $0 upfront deposit and $0 protocol fee.
  • Direct Voting: Always free ($0 protocol fee).
  • Optional Sponsorships (100% to Pool): Anyone (the creator via initialSponsorship or community sponsors via sponsorTopic(topicId, amount)) can optionally deposit USDC while voting is Open to fund free offline voting. 100% goes into SponsorEscrow with $0 deposit fee (funding an estimated ~10,000 valid offline votes per $100 sponsored at ~$0.01/vote).
  • Market-Updated Fee Parameters (Frozen per Topic): ~$0.01 / vote is an estimate—fee parameters are constantly updated to reflect market realities (gas, blob, and proving costs), while each topic freezes its paymentToken and pricePerVote at creation so active pools are never repriced mid-vote.

Revenue Split per Valid Vote (~$0.01 USDC Est.)

A voter claiming both their wallet and multiple validators in a single signed ballot counts as 1 valid vote (an estimated ~$0.01 total fee, regardless of ETH amount). For F = newlyAcceptedVoteCount * pricePerVote (illustrated at $0.01 / vote):

Recipient Share 1,000 Valid Votes (Est.) 10,000 Valid Votes ($100 Pool Est.)
Batch Prover (msg.sender) 65% $6.50 USDC $65.00 USDC
Vote Aggregator (batch.submitter) 35% $3.50 USDC $35.00 USDC

Pro-Rata Unused Refunds

Once all batches settle or settlementDeadline passes, unused sponsored funds U are locked for refunds. Each sponsor claims 100% of their exact pro-rata unused share via claimRefund(topicId): 

refund_i = floor(U * contributorEscrow[i] / totalEscrowContributed)
Operator Guides · Earn 35%

Run a Vote Aggregator

Vote Aggregators host frontends where ETH holders sign votes offline, bundle signed votes into Ethereum EIP-4844 blobs, and earn 35% of the per-vote fee from sponsored funds whenever those votes are proven valid.

Zero protocol fee at publication: Calling publishBatch requires no protocol deposit—you only pay standard Ethereum blob gas, and receive USDC payouts automatically when any prover settles your batch.

Architecture of an Aggregator

  1. Offline Voting UI & HTTP Intake: Serve a web UI using @therdal/sdk that prompts ETH holders to sign an EIP-712 Vote message offline (specifying resolutionId, chosen option index, deadline, and claimed wallet/validator positions).
  2. Pre-Queue Validation: Verify the voter's ECDSA signature and canonical encoding using BatchPublisher::submit_signed_vote so invalid spam never enters your blob payload.
  3. Blob Packing & Public Archival: Encode queued votes into THERDAL_BLOB_V1 blobs (up to 6 blobs / ~760 KB per batch) and expose the raw blob files on a public HTTP endpoint or IPFS gateway so permissionless provers can retrieve them even after the 18-day EIP-4844 beacon pruning window.
  4. On-Chain Registration: Submit a Type-3 blob transaction calling Therdal.publishBatch(resolutionId, blobCount) before votingEndsAt.

Operator Guides · Earn 65%

Run a Batch Prover

Batch Provers verify published vote blobs off-chain, generate cryptographic validity proofs, and call settleBatch on Ethereum to earn 65% of the per-vote fee from sponsored funds for every valid vote.

Non-sequential batch proving: You can prove any unsettled batchId in any order. If an aggregator publishes a malformed or unavailable blob, simply skip it—malformed batches never block honest batches and earn $0.

Prover Workflow

  1. Monitor Published Batches: Subscribe to BatchPublished(resolutionId, batchId, submitter, commitmentRoot, blobVersionedHashes) events on Therdal.sol.
  2. Ensure Snapshot Is Authenticated: Check resolutionState(resolutionId).snapshotAuthenticated. If false, fetch the RLP execution block header and beacon SSZ branch for the topic's snapshot block and call authenticateSnapshot once.
  3. Build State & Validator Witnesses: Decode the raw blob bytes from your beacon node or the aggregator's blob archive. Fetch EIP-1186 account proofs (eth_getProof) at snapshotBlockNumber and beacon validator SSZ proofs at snapshotEpoch for each claimed position.
  4. Generate Proof & Settle On-Chain: Run BatchProver::prove_batch against the current on-chain positionRoot and submit Therdal.settleBatch.

Protocol Specification

Batch & Blob Format

Canonical THERDAL_BLOB_V1 binary framing and KZG-to-STARK commitment binding for EIP-4844 vote batches.

Canonical 31-Byte Field Element Packing

Each EIP-4844 blob contains 4,096 BLS12-381 scalar field elements (131,072 bytes). Every 32-byte field element FE[k] MUST set byte 0 to 0x00 and carry 31 payload bytes in bytes 1..32, yielding 126,976 usable payload bytes per blob (maximum 6 blobs per batch).

Stream Binary Layout (THERDAL_BLOB_V1)

Byte Offset Field Type Description
0..8 magic [u8; 8] ASCII "THDLBLOB" (0x5448444c424c4f42)
8..12 version u32 (BE) Format version (1)
12..44 resolutionId u256 (BE) Target topic / resolution ID
44..52 batchId u64 (BE) Batch index registered on-chain
52..56 voteCount u32 (BE) Number of encoded VoteRecord items
56..60 payloadLen u32 (BE) Byte length of all encoded VoteRecord items
60..60+len records VoteRecord[] Length-prefixed canonical signed votes
60+len..end padding 0x00* Zero-byte trailing padding

KZG-to-STARK Binding

On-chain, BatchRegistry reads blobhash(i) and stores commitmentRoot = keccak256(abi.encodePacked(blobHashes)). Inside circuits/src/blob_binding.rs, the prover verifies that keccak256(concat(versionedHashes)) == commitmentRoot and checks the Fiat-Shamir barycentric polynomial evaluation opening against each blob's 0x01 KZG commitment.

StarkVerifierAdapter.sol and circuits/src/batch_transition.rs bind every settlement proof to a canonical 608-byte (19-word) public input digest.

Per-Vote Counting Rule (newlyAcceptedVoteCount)

  • A valid signed Vote envelope that contributes at least one newly counted ETH position (weight > 0 not yet present in oldPositionRoot) increments newlyAcceptedVoteCount by 1.
  • Claiming an execution wallet plus multiple validators in a single signed ballot increases ETH weight and newCountedPositions without multiplying the per-vote fee (~$0.01 estimated).
  • Invalid, expired, or 100%-duplicate votes increment newlyAcceptedVoteCount by 0.

Security & Threat Model

Core cryptographic settlement and escrow solvency invariants enforced on Ethereum L1.

Core Safety Invariants

  1. Cryptographic Settlement Invariant: Every tally update must verify a valid proof bound to an on-chain commitmentRoot, authenticated snapshotExecutionRoot / snapshotBeaconRoot, and the current 256-bit SMT positionRoot, guaranteeing every ETH position is counted at most once.
  2. Escrow Solvency Invariant: totalEarnedFees + remainingEscrow == totalEscrowContributed prior to refunds, and sum(refund_i) <= frozenUnusedEscrow after settlement closes.
