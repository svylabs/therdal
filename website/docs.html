Getting Started

Overview

Therdal is a permissionless and verifiable stakeholder signaling protocol for Ethereum—giving ETH holders a credible way to express nonbinding preferences without claiming formal governance authority.

Nonbinding by design: Therdal measures real ETH-weighted sentiment across regular wallets and staked validators without introducing coin-voting capture over Ethereum protocol upgrades.

Four Decoupled Protocol Stages

Therdal separates topic creation, voter signing, batch publication, and cryptographic proof settlement so no single actor is trusted and voters can participate offline for $0 gas:

  1. Create a Topic: Anyone publishes a question, defines custom voting choices, records the Ethereum block-header snapshot at creation, and seeds a refundable USDC vote pool.
  2. Cast a Vote: ETH holders select an option backed by both wallet ETH and validator stake—signing offline for $0 gas or voting directly.
  3. Aggregate & Publish: Permissionless aggregators host voting frontends, collect offline signatures, and post compressed vote batches into Ethereum EIP-4844 blobs.
  4. Prove & Settle: Permissionless provers generate cryptographic validity proofs verifying signatures, snapshot balances, and uniqueness—updating the L1 tally and routing sponsored USDC rewards.

Quickstart & CLI

Build the smart contracts, circuits, publisher, and prover locally, and run a complete end-to-end simulation of batch aggregation, out-of-order proving, and USDC fee splitting.

Prerequisites

  • Rust Toolchain (cargo, Rust 1.85+ / Edition 2024)
  • Foundry (forge, cast, anvil for Solidity contracts)
  • Python 3 or any static HTTP server to preview the web app locally

1. Run Smart Contract Tests

forge test -vv

2. Run Rust Circuit, Publisher & Prover Tests

cargo test --offline

3. Run the End-to-End Protocol Simulation

The demo-e2e command simulates free topic creation, optional USDC pool sponsorship, multi-position offline signing (wallets + validators), permissionless batch aggregation, malformed spam-batch immunity, out-of-order STARK proving, 25/25/50 USDC payouts, and unused sponsor refunds: 

cargo run --offline --bin therdal-cli -- demo-e2e

4. Launch the Website & Interactive App

python3 -m http.server 4173
# Website:          http://localhost:4173/website/
# Documentation:    http://localhost:4173/website/docs.html
# Interactive App:  http://localhost:4173/frontend/
Core Concepts

Topics & Custom Options

Topics on Therdal are not restricted to binary Yes/No ballots. Creators define the question and custom voting options when creating the topic.

Creating a Topic

When calling createResolution(ResolutionConfig) on Therdal.sol, the creator specifies:

  • Question & Options Metadata (questionURI): Content-addressed URI (IPFS / Arweave / canonical JSON) defining the topic title, summary, and indexed option labels (for example, ["12 Blobs", "9 Blobs", "Keep at 6 Blobs"] or ["60M Gas", "45M Gas", "36M Gas", "No Change"]).
  • Snapshot Reference: snapshotBlockNumber, snapshotBeaconTimestamp, and snapshotEpoch recording the Ethereum block headers at creation.
  • Lifecycle Windows: votingStartsAt, votingEndsAt, and settlementDeadline.
  • Payment Stablecoin & Optional Initial Sponsorship: Approved USD stablecoin (defaulting to USDC) and any optional initial sponsorship (creating a topic requires $0 deposit and $0 protocol fee).

Topic Lifecycle Phases

Phase Condition Permitted Actions
Open votingStartsAt <= now <= votingEndsAt Voters sign choices; aggregators call publishBatch; anyone calls sponsor or authenticateSnapshot.
Settling votingEndsAt < now <= settlementDeadline Provers call settleBatch in any batch order; sponsors can still top up if pool runs low.
Finalized All published batches settled Final tallies locked; contributors call claimRefund for unused pool shares.
ClosedForRefunds now > settlementDeadline Settlement grace window closed; unused sponsored funds unlocked for pro-rata refunds.
Core Concepts

Snapshots & ETH Eligibility

Therdal measures voting weight from Ethereum block headers recorded at topic creation—counting both execution-layer wallet balances and consensus-layer staked validators without locking anyone's ETH.

Moving or buying ETH afterward has no effect: Because balances are proven against the block headers recorded when the topic was created, transferring, selling, or buying ETH after topic creation neither increases nor decreases a voter's weight, and voters never lock their funds.

Two-Step Snapshot Authentication

  1. Record at Creation: createResolution records snapshotBlockNumber and snapshotBeaconTimestamp / snapshotEpoch with minimal gas overhead.
  2. Authenticate Before Settlement: Anyone calls authenticateSnapshot(topicId, SnapshotAuthProof) before the first batch settles:
    • Execution Root: Verified against blockhash(snapshotBlockNumber) or the EIP-2935 History Storage contract (0x0000F90827F1C53a10cb7A02335B175320002935), extracting stateRoot from the RLP execution header.
    • Beacon Root: Verified against the EIP-4788 Beacon Roots contract (0x000F3df6D732807Ef1319fB7B8bB8522d0Beac02) with SHA-256 SSZ Merkle branches confirming alignment to the exact same execution block hash.

Eligible ETH Positions

  • Execution Wallet Balances (THERDAL_WALLET): Proven via an EIP-1186 Merkle-Patricia Trie account proof against snapshotExecutionRoot where account == vote.signer. Weight equals exact snapshot balance in wei.
  • Beacon Validator Stakes (THERDAL_VALIDATOR): Proven via an SSZ Merkle inclusion branch against snapshotBeaconRoot. Requires slashed == false, activationEpoch <= snapshotEpoch < exitEpoch, and 0x01 or 0x02 withdrawal credentials matching vote.signer.

Zero Double-Counting (256-bit Sparse Merkle Tree)

Every counted wallet or validator key is inserted into the topic's on-chain 256-bit Sparse Merkle Tree (positionRoot). If a later vote or batch attempts to claim an already-counted wallet or validator, the prover circuit skips that duplicate position automatically (weight = 0 added).

Core Concepts

Sponsored Funds & Fee Split

Offline voting is free for ETH holders because each topic holds a sponsored USD stablecoin pool that pays aggregators and provers per verified valid vote.

Free Topic Creation & Optional Sponsorships

  • Always Free Topic Creation ($0 Fee): Anyone can create a topic or referendum on Ethereum with $0 upfront deposit and $0 protocol creation fee.
  • Direct Voting: Always free ($0 protocol fee).
  • Optional Sponsorships (100% to Pool): Anyone (the creator or community sponsors) can optionally deposit USDC at creation or call sponsor(topicId, amount) to fund free offline voting. 100% goes into SponsorEscrow with $0 deposit fee (funding an estimated ~10,000 valid offline votes per $100 sponsored at ~$0.01/vote).
  • Market-Updated Fee Parameters (Frozen per Topic): ~$0.01 / vote is an estimate—fee parameters are constantly updated to reflect market realities (gas, blob, and proving costs), while each topic freezes its paymentToken and pricePerVote at creation so active pools are never repriced mid-vote.

Revenue Split per Valid Vote (~$0.01 USDC Est.)

A voter claiming both their wallet and multiple validators in a single signed ballot counts as 1 valid vote (an estimated ~$0.01 total fee, regardless of ETH amount). For F = newlyAcceptedVoteCount * pricePerVote (illustrated at $0.01 / vote):

Recipient Share 1,000 Valid Votes (Est.) 10,000 Valid Votes ($100 Pool Est.)
Batch Prover (msg.sender) 50% $5.00 USDC $50.00 USDC
Vote Aggregator (batch.submitter) 25% $2.50 USDC $25.00 USDC
Protocol (TherdalController) 25% $2.50 USDC $25.00 USDC

Pro-Rata Unused Refunds

Once all batches settle or settlementDeadline passes, unused sponsored funds U are locked for refunds. Each sponsor claims 100% of their exact pro-rata unused share via claimRefund(topicId): 

refund_i = floor(U * contributorEscrow[i] / totalEscrowContributed)
Operator Guides · Earn 25%

Run a Vote Aggregator

Vote Aggregators host frontends where ETH holders sign votes offline, bundle signed votes into Ethereum EIP-4844 blobs, and earn 25% of the per-vote fee from sponsored funds whenever those votes are proven valid.

Zero protocol fee at publication: Calling publishBatch requires no protocol deposit—you only pay standard Ethereum blob gas, and receive USDC payouts automatically when any prover settles your batch.

Architecture of an Aggregator

  1. Offline Voting UI & HTTP Intake: Serve a web UI using @therdal/sdk that prompts ETH holders to sign an EIP-712 Vote message offline (specifying resolutionId, chosen option index, deadline, and claimed wallet/validator positions).
  2. Pre-Queue Validation: Verify the voter's ECDSA signature and canonical encoding using BatchPublisher::submit_signed_vote so invalid spam never enters your blob payload.
  3. Blob Packing & Public Archival: Encode queued votes into THERDAL_BLOB_V1 blobs (up to 6 blobs / ~760 KB per batch) and expose the raw blob files on a public HTTP endpoint or IPFS gateway so permissionless provers can retrieve them even after the 18-day EIP-4844 beacon pruning window.
  4. On-Chain Registration: Submit a Type-3 blob transaction calling Therdal.publishBatch(resolutionId, blobCount) before votingEndsAt.

Step 1: Sign or Collect Offline Vote Envelopes

# Example: generate a signed offline vote JSON envelope via CLI
cargo run --offline --bin therdal-cli -- sign-vote \
  --private-key 0xac0974bec39a17e36ba4a6b4d238ff944bacb478cbed5efcae784d7bf4f2ff80 \
  --resolution-id 1 \
  --chain-id 1 \
  --choice 0 \
  --validator-indices 101 102 \
  --out ./votes/voter_1.json

Step 2: Pack Votes into Canonical EIP-4844 Blobs

# Validate signatures, pack canonical 31-byte field elements, and write to archive
cargo run --offline --bin therdal-cli -- publish-batch \
  --resolution-id 1 \
  --batch-id 0 \
  --archive-dir ./public-blob-archive \
  --vote-files ./votes/voter_1.json ./votes/voter_2.json

Step 3: Submit Type-3 Blob Transaction to Ethereum

# Register the blob batch on Therdal.sol (records msg.sender as batch.submitter)
cast send $THERDAL_ADDRESS "publishBatch(uint256,uint8)" 1 1 \
  --blob \
  --path ./public-blob-archive/res_1_batch_0.blob \
  --rpc-url $ETH_RPC_URL \
  --private-key $AGGREGATOR_PRIVATE_KEY

Operator Guides · Earn 50%

Run a Batch Prover

Batch Provers verify published vote blobs off-chain, generate cryptographic validity proofs, and call settleBatch on Ethereum to earn 50% of the per-vote fee from sponsored funds for every valid vote.

Non-sequential batch proving: You can prove any unsettled batchId in any order. If an aggregator publishes a malformed or unavailable blob, simply skip it—malformed batches never block honest batches and earn $0.

Prover Workflow

  1. Monitor Published Batches: Subscribe to BatchPublished(resolutionId, batchId, submitter, commitmentRoot, blobVersionedHashes) events on Therdal.sol.
  2. Ensure Snapshot Is Authenticated: Check resolutionState(resolutionId).snapshotAuthenticated. If false, fetch the RLP execution block header and beacon SSZ branch for the topic's snapshot block and call authenticateSnapshot once.
  3. Build State & Validator Witnesses: Decode the raw blob bytes from your beacon node or the aggregator's blob archive. Fetch EIP-1186 account proofs (eth_getProof) at snapshotBlockNumber and beacon validator SSZ proofs at snapshotEpoch for each claimed position.
  4. Generate Proof & Settle On-Chain: Run BatchProver::prove_batch against the current on-chain positionRoot and submit Therdal.settleBatch.

Step 1: Authenticate Topic Snapshot (If Needed)

cast send $THERDAL_ADDRESS \
  "authenticateSnapshot(uint256,(bytes,bytes32,bytes32,bytes32[],bytes32[],uint256))" \
  1 "$SNAPSHOT_AUTH_PROOF_TUPLE" \
  --rpc-url $ETH_RPC_URL \
  --private-key $PROVER_PRIVATE_KEY

Step 2: Generate Batch Validity Proof in Rust

use therdal_archive::BlobArchive;
use therdal_prover::BatchProver;

let archive = BlobArchive::new("./public-blob-archive")?;
let mut prover = BatchProver::default();

// Synchronize `prover.smt`, `prover.tallies`, and `prover.counted_positions`
// with the current on-chain ResolutionState before proving target `batch_id`:
let settlement = prover.prove_batch(
    &archive,
    chain_id,
    resolution_id,
    ruleset_version,
    batch_id,
    snapshot_epoch,
    voting_ends_at,
    snapshot_execution_root,
    snapshot_beacon_root,
    &wallet_witnesses,
    &validator_witnesses,
    price_per_vote_usdc_micros,
)?;

println!(
    "Valid votes proven: {} | Prover reward: ${:.2} USDC",
    settlement.newly_accepted_vote_count,
    settlement.prover_share_usdc_micros as f64 / 1_000_000.0
);

Step 3: Submit On-Chain Settlement & Collect 50% Fee Share

cast send $THERDAL_ADDRESS \
  "settleBatch(uint256,uint256,bytes32,uint256[3],uint256,uint256,bytes)" \
  $RESOLUTION_ID \
  $BATCH_ID \
  $NEW_POSITION_ROOT \
  "[$TALLY_0,$TALLY_1,$TALLY_2]" \
  $NEW_COUNTED_POSITIONS \
  $NEWLY_ACCEPTED_VOTES \
  $PROOF_BYTES \
  --rpc-url $ETH_RPC_URL \
  --private-key $PROVER_PRIVATE_KEY
Protocol Specification

Batch & Blob Format

Canonical THERDAL_BLOB_V1 binary framing and KZG-to-STARK commitment binding for EIP-4844 vote batches.

Canonical 31-Byte Field Element Packing

Each EIP-4844 blob contains 4,096 BLS12-381 scalar field elements (131,072 bytes). Every 32-byte field element FE[k] MUST set byte 0 to 0x00 and carry 31 payload bytes in bytes 1..32, yielding 126,976 usable payload bytes per blob (maximum 6 blobs per batch).

Stream Binary Layout (THERDAL_BLOB_V1)

Byte Offset Field Type Description
0..8 magic [u8; 8] ASCII "THDLBLOB" (0x5448444c424c4f42)
8..12 version u32 (BE) Format version (1)
12..44 resolutionId u256 (BE) Target topic / resolution ID
44..52 batchId u64 (BE) Batch index registered on-chain
52..56 voteCount u32 (BE) Number of encoded VoteRecord items
56..60 payloadLen u32 (BE) Byte length of all encoded VoteRecord items
60..60+len records VoteRecord[] Length-prefixed canonical signed votes
60+len..end padding 0x00* Zero-byte trailing padding

KZG-to-STARK Binding

On-chain, BatchRegistry reads blobhash(i) and stores commitmentRoot = keccak256(abi.encodePacked(blobHashes)). Inside circuits/src/blob_binding.rs, the prover verifies that keccak256(concat(versionedHashes)) == commitmentRoot and checks the Fiat-Shamir barycentric polynomial evaluation opening against each blob's 0x01 KZG commitment.

Protocol Specification

Proof Public Inputs

StarkVerifierAdapter.sol and circuits/src/batch_transition.rs bind every settlement proof to a canonical 608-byte (19-word) public input digest.

BatchPublicInputs Structure

struct BatchPublicInputs {
    uint256 chainId;
    uint256 resolutionId;
    uint32  rulesetVersion;
    bytes32 snapshotExecutionRoot;
    bytes32 snapshotBeaconRoot;
    uint256 batchId;
    bytes32 registeredBatchCommitment;
    bytes32 oldPositionRoot;
    bytes32 newPositionRoot;
    uint256[3] oldTallies;
    uint256[3] newTallies;
    uint256 oldCountedPositions;
    uint256 newCountedPositions;
    uint256 newlyAcceptedVoteCount;
}

Per-Vote Counting Rule (newlyAcceptedVoteCount)

  • A valid signed Vote envelope that contributes at least one newly counted ETH position (weight > 0 not yet present in oldPositionRoot) increments newlyAcceptedVoteCount by 1.
  • Claiming an execution wallet plus multiple validators in a single signed ballot increases ETH weight and newCountedPositions without multiplying the per-vote fee (~$0.01 estimated).
  • Invalid, expired, or 100%-duplicate votes increment newlyAcceptedVoteCount by 0.
Protocol Specification

Security & Threat Model

Core cryptographic settlement and escrow solvency invariants enforced on Ethereum L1.

Core Safety Invariants

  1. Cryptographic Settlement Invariant: Every tally update must verify a valid proof bound to an on-chain commitmentRoot, authenticated snapshotExecutionRoot / snapshotBeaconRoot, and the current 256-bit SMT positionRoot, guaranteeing every ETH position is counted at most once.
  2. Escrow Solvency Invariant: totalEarnedFees + remainingEscrow == totalEscrowContributed prior to refunds, and sum(refund_i) <= frozenUnusedEscrow after settlement closes.

Actor Threat Matrix

Actor Adversarial Vector Protocol Defense
Topic Creator Supplying forged execution or beacon state roots at creation Roots authenticated via BLOCKHASH/EIP-2935 & EIP-4788; topic creation charges $0 fee and 100% of optional sponsorships enter refundable escrow
Spam Submitter Publishing garbage blobs to stall settlement or drain sponsored funds Non-sequential settlement bypasses malformed batches; rewards require valid STARK proof (spam earns $0)
Censoring Frontend Dropping signed votes that favor an unwanted choice Voters can route offline votes to any competing aggregator or submit directly
Malicious Prover Splitting multi-validator votes to inflate per-vote fee payouts Voter ECDSA signature covers the entire envelope; replay blocked by SMT + batch.settled
Pricing Controller Raising per-vote fee retroactively on active topics paymentToken and pricePerVote frozen per topic at creation
